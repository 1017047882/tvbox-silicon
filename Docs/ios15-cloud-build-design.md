# iOS 15 兼容移植与 GitHub Actions 云构建方案

状态：已开始部署参数和实际编译流程的前置准备；完整兼容移植与 IPA 构建尚未完成。当前进度见 `Docs/ios15-build-preparation-usage.md`。

## 目标与已核实的项目基线

支持运行 iOS 15.0 及以上版本的 arm64 架构 iPhone、iPad 真机，尽量保留现有全部功能。使用 GitHub Actions 的 macOS 运行器生成可供后续签名侧载的 IPA。用户已明确：必须支持 iOS 15，并尽量保留全部功能。

本次检查的本地提交为 `2ffb56e`，远端地址为 `https://github.com/1017047882/tvbox-silicon`。当前检出的源码中没有 `.github` 工作流目录。本地 Windows 环境没有 Xcode 和 GitHub CLI，也未检测到 `GH_TOKEN` 或 `GITHUB_TOKEN` 环境变量。远端同步尚未成功，因此以下结论针对本地版本，不能据此认定它与上游最新版本一致。

`project.yml` 和根目录下的 Swift 包要求最低 iOS 17。`Packages/TVCore` 下的包文件和目录在 Git 中以符号链接保存，但 Windows 将它们检出为包含链接目标的普通文本文件。在 macOS Actions 运行器上通过 Git 检出，应能恢复这些符号链接。如果上传 ZIP 源码，则必须在运行 XcodeGen 前保留或明确重建这些链接。

静态搜索发现：40 个文件中存在 46 处 `@Observable` 声明，23 个应用文件使用了 iOS 15 之后才引入的导航 API。这些数量用于定位移植范围，并非经编译器确认的错误数量。

JVM、libffi、Unicorn 解释器、原生绑定、FFmpeg 和 Python wheel 的构建脚本同样将最低系统版本设为 iOS 17。NodeMobile 和 BeeWare Python 使用下载的预编译二进制，需要在 macOS 上检查其真实最低系统版本和导入符号。仅修改 Info.plist 无法让这些二进制获得兼容性。

## 可选路径与推荐意见

1. **推荐：对共享应用和核心模块进行向下兼容移植。** 保留业务逻辑和插件运行时，替换不支持的状态观察、导航 API，并为界面效果提供兼容实现。这条路径最接近原版功能，但需要根据编译器诊断修改多个文件。
2. **新增独立的 iOS 15 界面，共享核心模块。** 可隔离新旧界面改动，但会重复维护页面，增加完整功能同步的难度；核心模块的状态观察机制和原生库仍需移植。

直接编译未经修改的应用，只能作为 iOS 17 的构建基线，无法满足本次 iOS 15 验收要求。

## [Nova] 应用与核心模块改动

- 将 iOS 应用目标和 Swift 包的最低系统版本调整为 15.0，保留 macOS、tvOS 的现有目标版本。
- 评估固定版本的状态观察兼容库，例如 Perception，确认其与 Swift 6、现有状态归属模型兼容后再引入。统一迁移观察声明、绑定、环境注入和视图跟踪，不采用轮询代替状态观察。
- 为导航栈、路由路径和分栏布局提供 iOS 15 实现。优先评估维护中的导航兼容库能否适配现有路由枚举；若不适配，则使用明确的 NavigationView 适配实现。保留多级页面跳转和标签页状态。
- 为旧系统不支持的空状态界面、滚动定位、变更监听、符号动画、触觉反馈等 API 提供替代实现或可用性判断，在支持的系统上保留原有效果。
- 同时检查核心 API：正则表达式、时钟、按时长休眠以及较新的 Foundation、AVFoundation 接口，需要通过编译器验证或替换为兼容实现。
- 将订阅、直播与点播、搜索、收藏与历史、下载、云盘浏览，以及 JavaScript、JAR、Python、Node 源支持列为功能保留目标。依赖 iOS 15 缺失系统服务的功能，需要记录替代行为或明确限制；未经验证，不承诺全部功能完全一致。

## [Orian] 原生依赖兼容改动

- 将所有相关原生依赖脚本中的 iOS 真机和模拟器切片调整为面向 iOS 15 构建，不改变 tvOS 部署版本。
- 检查每个预编译框架的 Mach-O 构建版本和依赖。必要时重新编译，或选择经过验证的兼容版本；禁止仅降低二进制元数据中的版本号来掩盖不兼容。
- 固定依赖版本和哈希值。缓存键包含部署版本、运行器架构、Xcode 版本及依赖构建输入，防止 iOS 17 缓存混入 iOS 15 产物。
- 上游现有脚本包含递归清理命令。根据本工作区禁止递归删除的约束，不执行这些命令；执行前将相关步骤改为使用全新、独立的输出目录，或采用不删除已有内容的复用方式。

## [Lyra] GitHub Actions 云构建流程

- 使用兼容的 arm64 macOS 运行器，通过手动触发启动工作流。上游 JVM 的引导 JDK 和原生构建配置假定使用 arm64；固定运行器标签前，先核实可用标签及 Xcode 版本。
- 工作流默认使用仓库只读权限。检出指定提交，并在构建产物中记录提交号、工具链和依赖版本；不自动发布正式版本。
- 将原生运行时准备与应用编译分开，便于缓存耗时产物、独立定位失败。安装 XcodeGen、所需 JDK、Maven、原生构建工具和匹配版本的宿主 Python。
- 启用编译器 API 可用性检查，构建核心模块与 iOS 应用。生成完整功能产物时，缺少必需运行时应直接失败，不能只接受上游脚本的可选运行时警告。
- 禁用签名构建真机应用，按 `Payload/<app>.app` 结构暂存，压缩为未签名 IPA。上传前检查应用包、可执行文件和嵌入框架，再将 IPA、日志、依赖清单及校验和作为工作流产物上传。
- 未签名 IPA 需要通过可信工具另行签名和侧载，例如 SideStore、AltStore 或用户指定的其他工具。它不能直接安装，也不是 TestFlight 安装包。不索取 Apple 账号密码，不将凭据写入仓库。

## [Argus] 静态检查与构建验收

- 校验工作流语法、Shell 语法、符号链接和 XcodeGen 输入。
- 在合适的 macOS 运行器上执行现有核心回归测试，并针对兼容行为变化补充测试，避免编写仅重复实现逻辑的测试。
- 以最低系统版本 15.0 编译，并启用 API 可用性诊断。检查应用的 `MinimumOSVersion`、arm64 架构，以及所有嵌入 Mach-O 文件的最低系统版本。必要时检查导入的新系统符号及其可用性保护。
- 上传完整失败日志。工作流配置有效或存在 IPA 压缩包，都不能单独证明编译成功或运行兼容。

## [Pulse] 可测性评估与运行验证

现有核心测试可作为起点。识别路由与状态转换、兼容实现选择、兼容映射等纯函数，进行确定性的单元测试。对包含多个条件的兼容分支，按需设计能验证各条件独立影响判定结果的 MC/DC 用例。本项目是消费类应用，尚未建立汽车功能安全 ASIL 等级或 MC/DC 认证范围。

在 iOS 15 真机上验证：冷启动、标签页导航、通过 URL 导入订阅、搜索、直播与点播、拖动进度、音轨和字幕选择、画中画、收藏与历史持久化、下载续传、离线播放，以及各类插件运行时。异常用例包含订阅格式错误、源不可用、网络中断、操作取消及前后台切换。共享代码变更后，还需回归较新 iOS 上的导航与播放。

所选较新 Xcode 不一定能安装 iOS 15 模拟器运行时。将部署目标设为 15.0 并编译通过，不能代替真机验证。最终交付状态必须分别说明：是否编译通过、是否完成签名、是否安装成功、是否完成真机测试。

## 所需外部条件

- 一个有写入权限的 GitHub 仓库，以及执行其 Actions 工作流的方式。本地 `origin` 地址本身不能证明仓库归属或已具备推送权限。
- 用于安装的签名与侧载方式，以及用于运行验收的 iOS 15 设备。第一份云构建产物可以不签名，无需 Apple 签名密钥。

## [Raven] 实施顺序与验证方式

1. 确认兼容方案和用于构建的 GitHub 仓库 → 验证：明确功能保留范围、仓库写入权限及 Actions 执行方式。
2. 根据云端编译器诊断，移植状态观察、导航和核心 API → 验证：兼容代码编译通过，相关单元测试与核心回归测试通过。
3. 调整并构建面向 iOS 15 的全部原生依赖 → 验证：检查二进制最低系统版本、架构和依赖符号。
4. 通过 Actions 构建、检查并上传未签名 IPA → 验证：应用包结构、嵌入运行时、日志及校验和齐全。
5. 签名、安装并执行真机验收清单 → 验证：记录各项功能结果及仍存在的限制。
